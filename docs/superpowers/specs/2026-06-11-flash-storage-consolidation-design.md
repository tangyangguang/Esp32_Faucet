# Flash 存储收敛设计

本文定义 4MB ESP32 固件下业务 Flash/LittleFS 存储的收敛方案。目标是在不过度设计的前提下，兼顾历史记录可靠性、Flash 寿命和可维护性。

## 目标

- 出水记录每次出水结束立即保存，不能因为节流策略主动丢失。
- 出水记录只保存必要事实和计量方案 ID，不保存每条记录的完整计量参数快照。
- 已保存完整脉冲明细和长期样本库合并为同一件事，固定 5 条。
- 计量方案使用固定工程容量，超出后允许覆盖早期非当前方案。
- 统计和滤芯累计保持当前低频 NVS 保存方式，不引入复杂重建逻辑。
- 旧文件不迁移、不自动删除；不可读时给出清晰原因。

## 非目标

- 不做数据库式日志、复杂索引、压缩或后台 GC。
- 不从旧出水记录/旧计量快照文件迁移历史数据。
- 不承诺产品层面的固定记录条数；本文容量是当前 4MB 分区下的工程预算。
- 不为极端超量计量方案保留无限历史。

## LittleFS 预算

当前分区表中 LittleFS 分区为 `0x120000`，即 `1,179,648B`。

| 项目 | 工程预算 |
| --- | ---: |
| Esp32Base 文件日志，4 x 32KiB | 131,072B |
| 长期样本库，也就是已保存完整脉冲明细，5 条 | 约 82,864B |
| 本次校准会话样本区，3 条 | 约 49,728B |
| 出水记录校准元数据，512 条 | 约 32,792B |
| 当前校准会话状态 | 约 372B |
| 计量方案，100 条 | 约 9,632B |
| LittleFS/临时文件/异常余量 | 约 65,536B |
| 出水记录，20,000 条 x 36B + header | 约 720,024B |
| 剩余余量 | 约 87,628B |

预算结论：当前 4MB 分区下，出水记录工程容量定为 20,000 条成立。这个数不是产品约束；如果后续分区、样本容量或日志策略改变，应重新计算。

## 出水记录

出水记录使用新版文件，例如：

```text
/faucet_records_v2.bin
```

记录格式保持紧凑，目标为 36B/条。旧记录中的 `pulsePerMlAtRun` 不再作为历史计量事实保存，新版记录应保存 `meteringSchemeId`。记录包含：

- 开始时间或启动内相对时间。
- 出水量、目标值、有效脉冲数、过滤脉冲数。
- 持续时间、模式、结果、预设编号。
- 当时使用的计量方案 ID。
- 未同步时间时的 boot id。

写入规则：

- 每次出水结束立即写一条出水记录。
- 20,000 条定长环形覆盖，满后覆盖最旧记录。
- 保持简单文件头，允许保存 `count` 和 `oldestIndex`。
- 不做每条记录 `sequence/checksum`，避免扩大单条记录并挤压容量。
- 如果极低概率断电发生在写入窗口，允许最后一条记录异常；若未来要求最后一条也强保证，再评估 FRAM 或断电保持电容。

出水记录写失败时：

- 不改变本次出水控制结果。
- 统计和滤芯累计仍按真实出水更新并保存。
- Web/状态页提示“最近一次出水记录保存失败”。
- 系统日志记录错误。
- 不标记当前计量方案 `usedEver`，因为没有成功记录引用该方案。

## 计量方案

计量方案固定 100 条工程容量，业务页面不显示固定空位。

规则：

- 新方案永远分配新 ID，不复用旧 ID。
- 当前启用方案永远不能覆盖。
- 优先使用空槽。
- 满了后覆盖 ID 最小的停用非当前方案。
- 如果没有停用非当前方案，覆盖 ID 最小的非当前方案。
- 如果除了当前方案外没有可覆盖对象，创建新方案失败并提示存储空间不足。

历史记录引用的方案被覆盖后：

- 出水记录基础信息仍正常显示。
- 计量方案区域显示“计量方案已被覆盖，历史参数不可查看”。
- 不尝试从出水记录恢复历史计量参数，因为记录不保存完整快照。

已使用方案的正常修改规则：

- 名称、停用状态等非计量字段可以在原方案上更新。
- 影响计量的参数修改应创建新方案 ID。
- `usedEver` 是低频使用状态，不维护精确使用次数和最近使用时间。

## 样本和脉冲明细

不再维护独立的“已保存脉冲明细”池。长期样本库就是已保存完整脉冲明细。

- RAM 只保留最近 1 条完整脉冲明细。
- 本次校准会话样本区固定 3 条，可被新会话覆盖。
- 长期样本库固定 5 条，不自动覆盖。
- 长期样本库满时提示用户清理或放弃保存。
- 单条完整明细最多 4096 个原始边沿。

旧的 `kSavedPulseTraceMaxCount = 12` 属于旧通用明细库设计，新实现应删除或并入长期样本库，不再作为独立 Flash 占用。

## 统计和滤芯

统计和滤芯累计保持当前方案：

- 出水过程中不写 NVS。
- 出水结束后更新 RAM 中的统计和滤芯累计。
- 出水结束后保存 `faucet_stat` 和 `faucet_run` 到 NVS。
- 按每天 3-20 次的实际频率，这个写入量可以接受，不需要节流或从记录重建。

Web 趋势、分布和最近 30 天统计继续可以从出水记录临时聚合。NVS 中的 `totalMl` 继续作为总累计快速事实源。

## 旧文件和错误提示

旧文件不迁移、不自动删除、不自动格式化 LittleFS。

页面和 API 使用少量清晰状态：

- 无历史数据：文件不存在或记录数为 0。
- 历史记录格式不兼容：magic、version、recordSize 或容量不符合当前格式。
- 历史记录数据可能损坏：文件大小异常、头部异常或读文件失败。
- 部分记录已跳过：整体可读，但部分槽位不可用。
- 计量方案已被覆盖或不可查看：记录中的 `meteringSchemeId` 找不到对应方案。

这些状态只用于提示和诊断，不触发自动修复。

## 代码改造边界

实施时应重点收敛以下部分：

- 新增或替换出水记录 V2 存储格式，记录中直接保存 `meteringSchemeId`。
- 停止新写 `/faucet_record_metering_v1.bin` 和 `WaterRecordMeteringSnapshot`。
- 将长期样本库容量调整为 5 条，并移除旧 12 条保存明细池。
- 将计量方案存储改为 100 条固定工程容量和覆盖规则。
- 保持统计/滤芯 NVS 保存大方向不变，只拆清错误状态。
- Web 详情页按方案 ID 查方案；找不到时显示方案已覆盖或不可查看。

## 验证要求

- Native 测试覆盖出水记录 20,000 条环形覆盖和分页读取。
- Native 测试覆盖记录中 `meteringSchemeId` 保存和 Web 查询缺失方案的显示路径。
- Native 测试覆盖计量方案 100 条满后的覆盖优先级。
- Native 测试覆盖长期样本库 5 条容量满提示。
- Native 测试覆盖旧格式/坏文件的状态分类。
- 构建验证至少运行 native 测试和 ESP32 编译；需要上板时优先使用 `pio run -e esp32dev -t webota`。
